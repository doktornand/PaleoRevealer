🦕 Jurassic Mode — DeadCode Resurrection

PaleoRevealer
Scadassembler v2.0

Framework de migration ASM x86 16-bit (MS-DOS) → ASM x86 32-bit (Win32), avec support des formats binaires MZ/COM, moteur de règles hiérarchiques JSON, plugins IoT/SCADA et génération PE directe.

Langage : JavaScript (Node.js ≥14)
Dépendances : 0 (aucune !)
Licence : MIT
Cible : x86 16→32 bit
Formats in : .ASM / .COM / .EXE (MZ)
Formats out : MASM / NASM / PE binaire

Vue d'ensemble #

PaleoRevealer (fork étendu de Scadassembler) est un outil de résurrection de code mort — il permet de migrer des programmes assembleur DOS des années 80-90 vers Win32 modern, en particulier pour les systèmes embarqués, SCADA et IoT industriels.

Objectif principal
Migration legacy

Convertir des programmes ASM 16-bit (DOS) en code ASM 32-bit assemblable avec MASM ou NASM, ou générer directement un exécutable PE Win32.

Domaine cible
SCADA & IoT

Spécialisé dans les drivers matériels (ports série/parallèle, timers, PLC) et les systèmes de contrôle industriels à migrer.

Différenciation
DeadCode Revival

Le « Jurassic Mode » permet de ressusciter du code considéré comme perdu : binaires sans source, .COM TSR, programmes MZ avec segments multiples.

Architecture clé
Règles JSON hiérarchiques

11 catégories de règles avec cascade, résolution de conflits par priorité et extensibilité totale sans modifier le code JavaScript.

Qu'est-ce que PaleoRevealer fait exactement ?

Concrètement, l'outil prend en entrée :

  • → Un fichier source .ASM MS-DOS (instructions 16-bit, segments, interruptions DOS…)
  • → Un binaire .EXE (format MZ) sans code source disponible
  • → Un programme .COM (format plat, max 64 Ko)

Et produit en sortie :

  • ← Un fichier MASM (.asm) assemblable avec ML.exe / MASM32
  • ← Un fichier NASM (.asm) assemblable avec nasm.exe
  • ← Un binaire PE Win32 (.exe) directement exécutable
  • ← Un rapport JSON des transformations, warnings et review manuelles requises

Installation & démarrage #

PaleoRevealer n'a aucune dépendance npm. Il tourne avec Node.js natif ≥ 14. L'installation se résume à cloner et lancer.

Prérequis

Obligatoire
Node.js ≥ 14.0.0

Vérifié dans package.json via le champ engines. Aucun module externe requis.

Facultatif (pour assemblage)
MASM32 / NASM

Pour assembler le code généré. PaleoRevealer génère la source, pas besoin d'assembleur pour la conversion.

Clonage et démarrage

# 1. Cloner le dépôt
git clone https://github.com/doktornand/PaleoRevealer.git
cd PaleoRevealer

# 2. Installer les dépendances (aucune, mais npm install finalise le projet)
npm install

# 3. Tester l'installation
node cli.js --help

# 4. Lancer la suite de tests
npm test
npm run test:mz     # tests du parser MZ uniquement
npm run test:rules  # tests du moteur de règles

Premier test — conversion source ASM

# Conversion la plus simple : source ASM 16-bit → MASM 32-bit
node cli.js mon_programme.asm

# Avec rapport JSON et format NASM
node cli.js -f nasm --report -o sortie.asm mon_programme.asm

# Binaire MZ → PE Win32 (résurrection depuis binaire)
node cli.js --mz-to-pe -o nouveau.exe vieux_programme.exe

# Programme .COM TSR → PE
node cli.js --com-to-pe -o moderne.exe ancien_tsr.com
💡

Le point d'entrée principal est src/core/converter.js (déclaré dans package.json → "main"). La CLI est dans cli.js à la racine, installable globalement via npm link (commande : scadassembler).

Pipeline de conversion — 5 phases #

Chaque fichier entrant traverse séquentiellement 5 phases. Cliquez sur une phase pour en voir les détails.

Chargement
Détection format
PHASE 02
Analyse
CFG + Dataflow
PHASE 03
Transformation
Rule Engine
PHASE 04
Émission
Backend codegen
PHASE 05
Validation
Cohérence & review

Phase 1 — Chargement (Loader)

Le loader détecte automatiquement le format d'entrée et dispatche vers le parser approprié.

  • Détection par magic bytes : 0x4D 0x5A → MZ, analyse de l'en-tête DOS complet (28+ bytes)
  • Lecture de la table de relocation MZ (entrées de 4 bytes : segment:offset)
  • Extraction de l'entry point (CS:IP relocalisé), de la pile (SS:SP) et des segments logiques
  • Pour .COM : chargement de l'image plate 64K, simulation du PSP à l'offset 0x100
  • Pour .ASM : parsing du source texte ligne par ligne
  • Détection heuristique des zones code/data dans les binaires sans symboles

Phase 2 — Analyse statique

Construction des représentations intermédiaires nécessaires aux règles de transformation.

  • CFG Builder : graphe de flux de contrôle, blocs de base, arêtes de branchement
  • Dataflow Analyzer : calcul des valeurs live/dead des registres, dépendances entre instructions
  • Pattern Detector : reconnaissance des idiomes SCADA (accès ports I/O, boucles polling, drivers série)
  • Score de complexité calculé (utilisé comme condition dans les règles JSON)
  • Détection des far calls, interruptions DOS/BIOS, instructions BCD obsolètes

Phase 3 — Transformation (Rule Engine)

Cœur du framework : application des 11 catégories de règles en cascade, du plus prioritaire au moins prioritaire.

  • Cascade : architecture_rules → format_rules → domain_rules → … → fallback_rules
  • Chaque règle évalue sa condition sur le contexte courant de l'instruction
  • En cas de conflit, priority_override : la règle de priorité la plus haute l'emporte
  • Conflit à même priorité → marquage UNRESOLVED, review manuelle requise
  • Les plugins (BCD, FarCall, IoT, INT) sont invoqués depuis cette phase

Phase 4 — Émission (Backends)

Le résultat des transformations est rendu dans le format cible.

  • MASM backend : génère un .asm avec prologue .386 / .MODEL FLAT, STDCALL, headers Win32, directives MASM valides
  • NASM backend : syntaxe NASM, sections [section .text], extern pour les imports Win32
  • PE backend : construction directe du binaire PE (headers DOS stub + PE signature + COFF header + Optional header + sections)
  • Insertion de commentaires de contexte (instruction originale, raison de la transformation)
  • Marquage ;REVIEW: pour les transformations incomplètes nécessitant une relecture humaine

Phase 5 — Validation

Vérifications de cohérence post-génération avant livraison du résultat.

  • Vérification de la présence d'un point d'entrée valide dans le code généré
  • Validation que le modèle mémoire est bien FLAT (pas de références de segments résiduelles)
  • Présence des prototypes Win32 nécessaires (imports, EXTERN déclarations)
  • Comptage et rapport des transformations marquées ;REVIEW:
  • Génération du rapport JSON si --report est activé

Formats binaires — MZ & COM #

L'une des capacités phares de PaleoRevealer est de travailler directement sur les binaires DOS, sans code source. Le format MZ est décodé champ par champ.

Format MZ — Structure complète

Offset Taille Champ Utilisation par PaleoRevealer
0x002 B Magic "MZ" Vérification du format
0x022 B lastPageBytes Calcul taille image programme
0x042 B pagesInFile Calcul taille : pages × 512
0x062 B relocationCount Nb entrées table de relocation
0x082 B headerParagraphs Offset début programme = × 16
0x142 B initialIP Entry point (partie offset)
0x162 B initialCS Entry point (partie segment)
0x3C4 B e_lfanew Offset header PE (si NE/PE embarqué)

Conversion MZ → PE : les calculs clés

// Taille de l'image programme
const program_size = pagesInFile * 512
  - (lastPageBytes ? 512 - lastPageBytes : 0)
  - headerParagraphs * 16;

// Entry point physique DOS
const ep_physical = (loading_segment + initialCS) * 16 + initialIP;

// Conversion relocation MZ → RVA PE
// Entrée MZ : {segment: 0xXXXX, offset: 0xYYYY}
const rva = segment * 16 + offset;

// Mapping segments DOS → sections PE
// CODE  → .text  (EXECUTE | READ)
// DATA  → .data  (READ | WRITE)
// BSS   → .bss   (READ | WRITE | uninitialized)

Format COM — spécificités

📌

Un fichier .COM est une image mémoire plate : pas de header, pas de segments, pas de table de relocation. Il est chargé à l'offset 0x100 du segment de code (le PSP occupe les 256 premiers bytes). Tous les offsets internes sont donc relatifs à 0x100.

// Conversion .COM → PE
const com_entrypoint_rva = 0x100;  // PSP simulé si nécessaire

// Pour chaque offset interne dans le .COM :
const pe_rva = internal_offset - 0x100;
// Le PSP est simulé dans la section .data si le code y accède

Moteur de règles hiérarchiques #

C'est le composant central du framework. 11 catégories de règles JSON définissent entièrement le comportement de la conversion. Le moteur les évalue en cascade, du plus prioritaire au moins prioritaire.

Les 11 catégories et leur rôle

CatégoriePrioritéResponsabilitéExemple de transformation
architecture_rulesCRITICALChangement 16→32 bit, élimination de la segmentationAX → EAX, MOV AX,BX → MOV EAX,EBX
format_rulesCRITICALConversion .COM/.EXE → PE, relocationsPSP 0x100 → EntryPoint RVA, segments → sections
domain_rulesHIGHPatterns SCADA/IoT spécifiquesIN AL,0x3F8 → ReadFile(hCOM1,...)
pattern_rulesHIGHFar calls, BCD, hooks, chaînes $CALLF → CALL FAR PTR → réécriture flat
instruction_rulesMEDIUMConversion instruction par instructionLODSB → LODSB (inchangé ou équivalent 32-bit)
interrupt_rulesMEDIUMINT 21h, 10h, 16h → Win32 APIsINT 21h / AH=09h → WriteConsoleA()
register_rulesMEDIUMRegistres 16-bit → 32-bit, élimination segmentsDS:, ES:, SS: → suppression (flat model)
segment_rulesMEDIUMModèle mémoire segmenté → FLAT.MODEL SMALL → .MODEL FLAT, STDCALL
directive_rulesLOWDirectives CPU et mode.8086 → .386, .186 → .386
macro_rulesLOWTemplates et macros Win32Insertion de OPTION CASEMAP:NONE, imports DLL
fallback_rulesINFOMarquage tout ce qui n'a pas été traitéAjout de ;REVIEW: instruction non gérée

Structure JSON d'une règle

Chaque règle dans config/hierarchical_rules.json suit le schéma suivant :

{
  "id": "interrupt_dos_write_string",
  "name": "INT 21h / AH=09h → WriteConsoleA",

  "condition": {
    // Égalité simple
    "instruction": "INT",
    "operand": "21h",

    // Alternatives (OR logique)
    "register_ah": "09h | 0x09",

    // Comparateur numérique
    "complexity_score": { "gt": 3 },

    // Regex
    "source_pattern": { "regex": "^INT\\s+21h", "flags": "i" }
  },

  "transformations": {
    // Code source généré (tableau = lignes)
    "setup_code": [
      "    ; INT 21h/09h → WriteConsoleA",
      "    INVOKE WriteConsoleA, hStdOut, DX, -1, NULL, NULL"
    ],

    // Template avec variables
    "api_call": "WriteConsoleA(hStdOut, {dx_ptr}, {count}, NULL, NULL)",

    // Mapping registres
    "register_mapping": {
      "DX": "EDX",
      "AX": "EAX"
    }
  },

  // Avertissements inclus dans le rapport
  "warnings": [
    "Vérifier que hStdOut est bien initialisé avec GetStdHandle"
  ],

  // Effets de bord documentés
  "side_effects": [
    "Requiert INCLUDE windows.inc dans le prologue"
  ]
}

Ordre de cascade et résolution de conflits

// Ordre d'évaluation dans rule_engine.js
const CASCADE_ORDER = [
  "architecture_rules",   // 1er évalué → priorité absolue
  "format_rules",
  "domain_rules",
  "pattern_rules",
  "instruction_rules",
  "interrupt_rules",
  "register_rules",
  "segment_rules",
  "directive_rules",
  "macro_rules",
  "fallback_rules"       // Dernier → ramasse tout le reste
];

// Résolution de conflit
if (rule_A.priority === rule_B.priority) {
  result.status = "UNRESOLVED";   // → review manuelle
} else {
  // La plus haute priorité gagne (CRITICAL > HIGH > MEDIUM > LOW > INFO)
  winner = rule_A.priority > rule_B.priority ? rule_A : rule_B;
}

Plugins spécialisés #

Quatre plugins gèrent les cas particuliers qui dépassent les simples règles de remplacement d'instructions.

src/plugins/bcd_emulator.js
Émulateur BCD

Gère les instructions d'arithmétique décimale codée binaire du 8086, absentes du jeu d'instructions 32-bit modern.

  • AAA (ASCII Adjust for Addition)
  • AAS (ASCII Adjust for Subtraction)
  • AAM (ASCII Adjust for Multiply)
  • AAD (ASCII Adjust for Divide)
  • DAA / DAS (Decimal Adjust)

Ces instructions sont émulées par des séquences équivalentes 32-bit (comparaisons, masques AL, CF/AF manipulation).

src/plugins/farcall_resolver.js
Résolveur Far Calls

Gère les appels et sauts inter-segments (far calls) propres au modèle mémoire segmenté DOS, inexistants en mode FLAT Win32.

  • CALLF (far call avec segment:offset)
  • JMPF (far jump)
  • RETF (far return)
  • LDS, LES (load far pointer)

Stratégie : analyse du graphe d'appel pour convertir en CALL flat (near) quand possible, sinon marquage REVIEW.

src/plugins/iot_bridge.js
Bridge IoT / Matériel

Traduit les accès hardware bas niveau DOS vers les APIs Win32 modernes. Utilise config/iot_mappings.json.

  • Ports série (0x3F8/3E8) → CreateFile + ReadFile/WriteFile
  • Ports parallèle (0x378) → SetupComm / EscapeCommFunction
  • Timer 8253 (0x40-0x43) → SetTimer / timeSetEvent
  • Instructions IN/OUT → APIs ou DeviceIoControl
src/plugins/interrupt_dispatcher.js
Dispatcher d'interruptions

Analyse les interruptions DOS (INT 21h) et BIOS (INT 10h, 16h) et les mappe vers leurs équivalents Win32.

  • INT 21h/09h → WriteConsoleA
  • INT 21h/3Dh → CreateFileA (open)
  • INT 21h/3Ch → CreateFileA (create)
  • INT 21h/4Ch → ExitProcess
  • INT 10h/0Eh → WriteConsoleA (TTY)
  • INT 16h/00h → ReadConsoleA

Backends de sortie #

Trois formats de sortie sont disponibles, chacun ciblant un workflow différent.

Backend MASM
masm_backend.js

Génère du code assemblable avec ML.exe (Microsoft Assembler), JWASM, ou MASM32 SDK. Syntaxe avec macros INVOKE, includes windows.inc. Format cible par défaut.

Backend NASM
nasm_backend.js

Génère de la syntaxe NASM libre (Netwide Assembler). Sections [section .text], extern pour les imports DLL. Compatible Linux cross-compile.

Backend PE
pe_backend.js

Construit directement un binaire PE (.exe) Win32 valide sans passer par un assembleur intermédiaire. Utilise pe_builder.js et les templates JSON.

Exemples concrets #

Conversion la plus courante : un fichier source assembleur DOS 16-bit vers MASM 32-bit Win32.

; ENTRÉE : hello_dos.asm (assembleur MS-DOS 16-bit)
.MODEL SMALL
.STACK 100h
.DATA
    msg DB "Hello, World!", 0Dh, 0Ah, '$'
.CODE
start:
    MOV  AX, @DATA
    MOV  DS, AX
    MOV  AH, 09h       ; INT 21h fonction "Write String"
    LEA  DX, msg
    INT  21h
    MOV  AH, 4Ch       ; INT 21h fonction "Exit"
    INT  21h
END start
; SORTIE générée par PaleoRevealer : hello_win32.asm (MASM 32-bit)
.386
.MODEL FLAT, STDCALL
OPTION CASEMAP:NONE

INCLUDE windows.inc
INCLUDE kernel32.inc
INCLUDELIB kernel32.lib

.DATA
    msg DB "Hello, World!", 0Dh, 0Ah, 0  ; '$' → terminateur null
    ;REVIEW: vérifier encodage de la chaîne (CP437 → UTF-8 possible)

.CODE
start:
    ; INT 21h/09h → WriteConsoleA
    INVOKE GetStdHandle, STD_OUTPUT_HANDLE
    MOV   [hStdOut], EAX
    INVOKE WriteConsoleA, [hStdOut], OFFSET msg, SIZEOF msg - 1, NULL, NULL

    ; INT 21h/4Ch → ExitProcess
    INVOKE ExitProcess, 0
END start
# Commande
node cli.js -o hello_win32.asm --report hello_dos.asm
# Scénario : vous avez un vieux .EXE DOS sans le code source
# PaleoRevealer désassemble + convertit le binaire MZ
node cli.js --mz-to-pe -o moderne.exe --report vieux_dos.exe

# Ce que fait le pipeline :
# 1. Lecture du header MZ (magic "MZ", pages, relocations)
# 2. Extraction de l'image programme (code + data + bss)
# 3. Désassemblage heuristique (détection zones code/data)
# 4. Application des règles de transformation
# 5. Construction d'un nouveau header PE Win32 valide
# 6. Génération du binaire .exe
⚠️

La désassemblage de binaires sans symboles est heuristique. Des sections de données peuvent être interprétées comme du code. Le rapport --report signale les zones incertaines avec des marquages REVIEW.

# Mode SCADA : driver matériel avec accès ports I/O
node cli.js --scada --report -f masm -s CONSOLE device_driver.asm

; EXEMPLE : accès port série COM1 (0x3F8)

; AVANT (DOS 16-bit) :
    MOV  DX, 0x3F8    ; Port COM1 - Data register
    IN   AL, DX        ; Lire un byte depuis COM1

; APRÈS (généré avec --scada) :

Écrire ses propres règles JSON #

L'extension principale de PaleoRevealer se fait sans toucher au JavaScript : en modifiant config/hierarchical_rules.json. Voici le guide complet.

Étape 1 — Identifier le bon niveau de priorité

// Choisissez CRITICAL si votre règle doit s'appliquer avant tout
// → ex: une instruction impossible à gérer autrement

// Choisissez MEDIUM pour la plupart des conversions d'instructions
// → ex: une nouvelle interruption INT à mapper

// Choisissez LOW pour des directives ou macros complémentaires
// Choisissez INFO pour un marquage/documentation seulement

Étape 2 — Rédiger la condition

{
  "condition": {
    // Matcher une instruction précise :
    "instruction": "LODSB",

    // Ou plusieurs instructions (OR) :
    "instruction": "LODSB | LODSW | LODSD",

    // Ou une liste :
    "instructions": ["SCASB", "SCASW"],

    // Condition sur un operande :
    "operand_1": "AL",

    // Condition numérique :
    "pattern_confidence": { "gt": 0.8 },

    // Condition regex :
    "source_line": { "regex": "^\\s*IN\\s+AL", "flags": "i" }
  }
}

Étape 3 — Définir les transformations

{
  "transformations": {
    // Remplacement direct (string) :
    "replacement": "LODSB",   // inchangé ici

    // Séquence de lignes :
    "setup_code": [
      "    ; Ma transformation custom",
      "    INVOKE MonAPI, EAX, EBX"
    ],

    // Mapping de registres (appliqué par register_rules) :
    "register_mapping": {
      "SI": "ESI",
      "CX": "ECX"
    },

    // Template avec variables de contexte :
    "api_call": "MyAPI({operand_1}, {operand_2})"
  }
}

Étape 4 — Ajouter la règle dans la bonne catégorie

// Dans config/hierarchical_rules.json :
{
  "instruction_rules": {
    "_priority": "MEDIUM",
    "_description": "Conversion instruction par instruction",
    "rules": [
      // ... règles existantes ...
      {
        "id": "ma_nouvelle_regle",
        "name": "Description lisible",
        "condition": { "instruction": "MON_INSTRUCTION" },
        "transformations": { "replacement": "INSTRUCTION_WIN32" }
      }
    ]
  }
}
💡

Après modification du JSON, relancez simplement npm run test:rules pour vérifier que votre règle est valide et ne crée pas de conflits avec les règles existantes.

Étendre les plugins #

Les plugins sont des modules JavaScript simples dans src/plugins/. Voici comment en créer un nouveau.

Structure d'un plugin

// src/plugins/mon_plugin.js

class MonPlugin {
  constructor(config) {
    // config = le JSON de config/iot_mappings.json (ou autre)
    this.config = config;
  }

  /**
   * Méthode principale appelée par le Rule Engine
   * @param {Object} instruction - L'instruction en cours d'analyse
   * @param {Object} context - Contexte: registres, CFG, dataflow
   * @returns {Object|null} - Transformation ou null si non applicable
   */
  process(instruction, context) {
    // Exemple : matcher une instruction spécifique
    if (instruction.mnemonic === 'MON_MNEMONIC') {
      return {
        type: 'replacement',
        code: [
          `    ; Converti par MonPlugin`,
          `    INVOKE MonWin32API, EAX`
        ],
        warnings: ['Vérifier les paramètres de MonWin32API']
      };
    }
    return null;  // Pas applicable, passer à la règle suivante
  }

  /**
   * Hook appelé en début de fichier (prologue)
   */
  onFileStart(context) {
    return ['INCLUDE mon_include.inc'];
  }
}

module.exports = MonPlugin;

Enregistrer le plugin dans le pipeline

// Dans src/core/converter.js, section plugins :
const MonPlugin = require('../plugins/mon_plugin');

// Instanciation avec config optionnelle
const plugins = [
  new BCDEmulator(config),
  new FarCallResolver(config),
  new IoTBridge(config.iot_mappings),
  new InterruptDispatcher(config),
  new MonPlugin(config)   // ← Ajout ici
];
ℹ️

Les plugins sont appelés en premier lors de la phase 3 (Transformation), avant l'évaluation des règles JSON. Si un plugin retourne une transformation, le Rule Engine ne cherche plus de règle pour cette instruction (court-circuit).

Créer un nouveau backend #

Pour cibler un nouveau format de sortie (GAS, FASM, ARM, ou même du pseudo-code C), il suffit d'implémenter l'interface backend.

// src/backends/gas_backend.js — exemple pour GNU Assembler

class GASBackend {
  constructor(options) {
    this.options = options;
    this.output = [];
  }

  /** Prologue du fichier */
  emitPrologue() {
    this.output.push('# Généré par PaleoRevealer — backend GAS');
    this.output.push('.intel_syntax noprefix');
    this.output.push('.section .text');
    this.output.push('.global _start');
  }

  /** Émettre une instruction transformée */
  emitInstruction(transformed) {
    if (transformed.comment) {
      this.output.push(`    # ${transformed.comment}`);
    }
    if (transformed.review) {
      this.output.push(`    # REVIEW: ${transformed.review}`);
    }
    transformed.code.forEach(line => this.output.push(line));
  }

  /** Section données */
  emitDataSection(data) {
    this.output.push('.section .data');
    data.forEach(d => {
      this.output.push(`${d.name}: .byte ${d.values.join(', ')}`);
    });
  }

  /** Épilogue */
  emitEpilogue() {
    this.output.push('# Fin de la conversion');
  }

  /** Retourner le code final */
  getOutput() {
    return this.output.join('\n');
  }
}

module.exports = GASBackend;

Enregistrer et utiliser le nouveau backend

// Dans src/core/converter.js :
const backends = {
  masm: require('../backends/masm_backend'),
  nasm: require('../backends/nasm_backend'),
  pe:   require('../backends/pe_backend'),
  gas:  require('../backends/gas_backend')   // ← Nouveau
};

// Dans cli.js, ajouter l'option :
// -f, --format : masm | nasm | pe | gas

Limites actuelles #

PaleoRevealer est un outil puissant mais avec des contraintes inhérentes à la complexité du problème. Voici une analyse honnête des limites.

Limite critique
Désassemblage heuristique

Sur les binaires MZ sans symboles, la séparation code/données est heuristique. Des tableaux de données peuvent être désassemblés comme instructions, et vice versa. Le marquage REVIEW signal les zones douteuses mais ne les corrige pas.

Limite critique
Pas d'émulation complète

PaleoRevealer ne simule pas l'exécution. Les programmes avec auto-modification de code, chiffrement en mémoire, ou code généré à l'exécution ne peuvent pas être convertis.

Limite importante
Far calls complexes

Les far calls vers des adresses calculées dynamiquement (tables de vecteurs, pointeurs en RAM) ne peuvent pas être résolus statiquement. Ils sont marqués REVIEW.

Limite importante
API Win32 limitée

Seul un sous-ensemble d'APIs Win32 est supporté dans les règles (kernel32, user32 de base). Les appels à des DLLs spécifiques (DPMI, extended INT) nécessitent des règles custom.

Limite mineure
Pas de débogage symbolique

La conversion ne préserve pas les informations de débogage (PDB, COFF symbols). Le code généré est fonctionnellement équivalent mais sans symboles.

Limite mineure
Instructions FPU non couvertes

Les instructions co-processeur x87 (FILD, FSTP, FMUL…) ne sont pas dans les règles par défaut. À ajouter via règles custom ou plugin.

À noter
Zéro dépendances

Le choix de n'avoir aucune dépendance npm simplifie le déploiement mais signifie que certaines fonctionnalités (parsing ASM avancé, désassemblage précis) sont développées from scratch sans bibliothèques éprouvées.

À noter
Revue manuelle requise

PaleoRevealer n'est pas un outil "fire and forget". Tout output doit être relu, testé et validé par un développeur maîtrisant l'assembleur. C'est un outil d'assistance à la migration, pas un convertisseur automatique parfait.

Pistes d'extension (Roadmap) #

Idées et directions pour aller plus loin avec PaleoRevealer.

Extensions à court terme (sans modifier le core)

Règles JSON
Couvrir x87 FPU

Ajouter une catégorie fpu_rules dans le JSON pour les instructions co-processeur x87 (FILD, FSTP, FMUL, FLDCW…).

Mappings IoT
Nouveaux matériels

Enrichir iot_mappings.json avec des ports industriels supplémentaires : Modbus RTU, CANbus adapters, GPIO industrial.

Nouveau plugin
DPMI Support

Plugin pour les programmes DOS Protected Mode (DPMI) — applications DOS en mode protégé 32-bit, courantes dans les outils industriels des années 90.

Nouveau backend
GAS / LLVM IR

Backend GNU Assembler pour Linux (cross-compilation), ou même LLVM IR pour une optimisation ultérieure par LLVM.

Extensions à moyen terme (modifications du core)

Core — Analyse
Analyse de types

Inférence de types sur les données (pointeurs, entiers, structures) à partir de l'analyse dataflow, pour générer un code Win32 plus précis.

Core — Loader
Support NE / LE

Parser pour les formats NE (New Executable — Windows 3.x) et LE (Linear Executable — OS/2), proches du MZ mais plus complexes.

UI
Diff visuel

Affichage côte-à-côte de l'instruction originale et de sa version convertie dans l'interface web, avec mise en évidence des règles appliquées.

Tests
Corpus de benchmark

Constituer une bibliothèque de programmes DOS réels (libres de droits) pour benchmarker la qualité de la conversion de façon automatisée.

Vision long terme — "Jurassic Mode" complet

L'idée centrale du projet PaleoRevealer est de permettre la résurrection complète de programmes DOS dont le code source a été perdu. La vision à long terme inclut : un désassembleur symbolique (avec reconstruction partielle de noms de fonctions), une analyse sémantique pour identifier les algorithmes (tri, checksums, protocoles de communication), et une génération de code C moderne à partir de l'ASM converti. Un vrai "time machine" pour le code mort.
